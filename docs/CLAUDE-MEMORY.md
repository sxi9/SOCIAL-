Inspect with `ssh saibala@192.168.29.22 'cd ~/socialchat && docker compose logs --since 8h --no-log-prefix api'`; DB via `docker compose exec -T postgres psql -U socialchat -d socialchat` (pipe a .sql file over ssh stdin to avoid quoting pain). The api logs 4xx only as status codes (never the error code); `remotePort` in api logs is Caddy's pooled upstream port, not a client identity.  DEV MODE ON THE BOX IS DANGEROUS: on 2026-10-18 running next dev + tsx watch + tsc --watch there (~/socialchat-dev, scripts in ~/bc-dev: dev.sh / stop.sh / .env.dev pointing at the container bridge IPs 172.18.0.x, ports 3100 web / 3101 api, reached via `ssh -N -L 3100:127.0.0.1:3100`) pushed the already-swapped host into thrashing: SSH banner timeouts and the LIVE app stopped answering for 10+ minutes. Do not start the dev loop there again unless Firefox/leakwatch are closed and >2 GB is free; prefer dev on the laptop (Docker Desktop needs admin) or deploy-only. The host is chronically overloaded (Firefox + ~/leakwatch python eat the CPU, swap full), which made call hang-ups take 10-16 s on 2026-10-18.

Windows laptop tooling: `corepack enable` fails with EPERM (Program Files); use `npm i -g pnpm@10.28.0` and add `$(npm prefix -g)` to PATH in Git Bash. Docker Desktop's `com.docker.service` is stopped and needs admin to start, so server integration tests (need Postgres/Redis, and v1.0a needs MinIO) cannot run locally; CI has Postgres+Redis but no MinIO. **`pnpm -r build` can never pass on this laptop (2026-10-27):** pnpm runs package scripts under cmd.exe, and `apps/server`'s build script is `tsc && mkdir -p dist/db/migrations && cp …` — cmd has no `mkdir -p`/`cp`, so it fails with "The syntax of the command is incorrect" AFTER tsc succeeds (fine on CI/Docker, Linux). Verify locally with `pnpm exec tsc --noEmit -p tsconfig.json` in apps/server and apps/web (web's `lint` script is just that; there is no ESLint config, so `next build` has no lint step) plus `pnpm build` in apps/web; tests aren't in server tsconfig `include` — typecheck them via a temp tsconfig extending it. Never trust `pnpm … | tail` for an exit code (it reports tail's): log to a file and propagate `$?`.

**Why:** the user does local development here and deploys with `./bored update` on the box; knowing the layout avoids re-discovery.

**How to apply:** never run integration tests against the live DB; propose config changes on the box (PUBLIC_ORIGIN, restarts) rather than applying them unasked. See user saikrishna hardware.
